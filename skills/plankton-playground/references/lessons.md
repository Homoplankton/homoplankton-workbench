# 失败案例集 —— 开工前扫一眼

每条都是真实发生过、造成返工的事故。格式：现象 → 根因 → 教训。

---

## 1. 整页全黑（最严重）

**现象**：用户打开页面，纯黑，什么都没有。
**根因**：长卷高度公式 `area / 0.2` 漏除视口宽度，算出 2000 万像素高的页面（≈2 万屏），所有图随机撒在里面，首屏一张都落不进来。
**教训**：**语法检查通过 ≠ 页面能看**。必须有"首屏 ≥ N 张"这类可观察断言。任何涉及画布尺寸/坐标换算的改动，交付前跑无头仿真打印真实数值。

---

## 2. 裁切实验毁掉整批素材

**现象**：用户看硬盘上的裁切结果，主体被切掉一大块，"这是灾难"。
**根因**：裁切依据的主体框来自亮度阈值检测。透明水母、栉板的触须和羽状臂极淡，被阈值判成"背景"，框本身就切进了主体；框外再留 15% 边距也救不回来，因为基准错了。
**教训**：**不可逆的批量图像处理前，先出 6–9 张样张给用户过目**。尤其是"检测主体边界"这类对透明/低对比物体天然不可靠的操作。宁可多一轮确认，不要一次毁 93 张。

---

## 3. 三项同改导致重叠灾难

**现象**：用户说"到处都是重叠，这是灾难"，要求回退。
**根因**：一轮里同时改了密度（空隙率 1.5→1.25）、尺寸下限（+20%）、左右禁飞区，还顺手重写了预算机制。失败后无法归因是哪一项。
**教训**：**一次只改一个变量**。用户一次提三个需求时，也要拆成三次改动、三次验证。多项耦合改动出错，代价是整版回退。

---

## 4. 集体齐步走

**现象**：用户说"运动非常明显了，但随机性没了，所有图一起向右再一起向左"。
**根因**：为了"动得更明显"引入了全体共享的刚体平移（洋流）。相对位置恒定所以零碰撞很容易保证，但视觉上就是齐步走。
**教训**：**"动得更明显"应该加大每张图各自的幅度/频率差，不是让所有图同步**。同步平移是最省事的作弊，也是最容易被一眼看穿的。独立航迹 + 各自相位才是"漂浮"。

---

## 5. 方框叠方框

**现象**：用户滚动到深处，发现大量矩形图片互相叠压，"三处重叠，这是灾难"。
**根因**：防碰标准建在"生物主体框"上——照片的黑色暗边互相压叠被默认为可接受，指望羽化遮罩盖住。但主体偏心的照片（生物贴一角、其余全是暗边）一多，暗边交叠就露出矩形硬边。
**教训**：**碰撞口径必须等于用户眼睛看到的东西（图框），不是语义上的主体**。羽化能弱化边缘，不能替代分离。

---

## 6. 自作主张加 UI

**现象**：连续三轮被要求删除——标题 HOMOPLANKTON、底部统计、筛选按钮、图片类目标签、hero 大图、前景虚焦光斑、蓝黑水体底纹。
**根因**：把"作品集网站"默认理解成需要标题和导航，把"深海氛围"默认理解成需要底纹和景深光斑。
**教训**：**"纯净"类需求从最小实现起步**。用户没要的 UI 一律不加；想加先在方案里问，不要先做。这个产品的正确形态是：纯黑 + 漂浮生物 + 星尘，没有别的。

---

## 7. 底部小图堆积 / 上大下小

**现象**：用户滚动到底部，发现生物明显变小、变密。
**根因**：两个叠加机制。① 放置顺序是"大→小"，画布又"边放边扩容"，导致越晚放的小图被带到越下面；② 放置失败的图掉进"堆到画布最底部"的兜底逻辑，而失败的多是后期小图。
**教训**：**画布高度必须在放置前固定**，兜底路径也要走完整校验、且在目标带内找位。验证时要按纵向十等分统计每段平均尺寸与张数，不能只看全局均值。

---

## 8. 脚手架自身的 bug 冒充产品 bug

**现象**：仿真报"重叠""越界"，追查半天发现是测试脚本把图片左上角坐标当中心点算重叠、`style.height` 被 Proxy 吞掉读不到、`__dirname` 指错目录、变量未声明就引用。
**教训**：**验证工具本身也要验证**。断言失败先怀疑测量方式，再怀疑产品。测试脚本用编辑工具改，不要用 sed 打补丁（引号嵌套极易写坏且不留痕）。

---

## 9. 阈值断言卡死交付

**现象**：产品实际达标，但断言阈值是我早先随手定的（如"疏密变异系数 >0.2"、"首屏 ≥10 张"），密度提高后自然收窄，反复失败。
**教训**：断言阈值要绑定**用户可观察的语义**（"底部不能比顶部小"、"首屏要一眼看到很多生物"），不是绑定某次实现的中间数值。改产品参数时同步审视阈值是否还代表原意。

---

## 10. 中间产物撑爆系统盘

**现象**：写预览图时报 `No space left on device`，系统盘只剩 484MB。
**根因**：素材处理的 staging 副本（原图 231MB + 显示层 231MB）留在项目目录，加上多版本 history 快照。
**教训**：**大体积中间副本用完即删**，或明确告知用户占用并请求批准清理。上传成功、外链生成后，staging 副本就没有保留价值。每次定版前查一次磁盘余量。

---

## 11. 显示层阶梯方向写反，整页加载 256MB 原图

**现象**：104 张测试跑完，页面打开先纯黑数秒，然后图片一张张蹦出；`report.json` 里 `display_used_original: 104`，`src == full` 全部相同，线上单张 3.3MB，全页 256MB。
**根因**：`make_display` 的质量阶梯为凑够「≥1MB 下限」而把长边从 2000 **逐级缩到** 1200——缩小只会让文件更小，五档必然全败，于是 `shutil.copy2` 把原图塞进显示层。v23 侥幸没暴露，只因那批源图长边本就约 1500px、首档即达标；换成中位长边 3692px 的批次立刻全线回退。
**教训**：
- **「≥1MB」是错误的显示层指标。** 屏幕图块只有 162–206px，为凑字节数去保留 7000px 原图毫无收益。主控变量必须是**长边像素**，字节数只能当「不许放大凑数」的护栏。
- **单调性检查**：任何「逐级尝试直到满足阈值」的循环，都要先确认调整方向与阈值方向一致。若阈值是下限而你在缩小，这个循环在设计上就不可能成功。
- **基线侥幸 ≠ 逻辑正确**：v23 达标不能证明阶梯正确，只说明那批素材没触发失败分支。换新素材批次时，`display_used_original` 必须是交付前的强制检查项，非 0 即视为素材门未过。

## 12. 环境反复试探吃掉大量时间

**现象**：`prep_assets.py` 连报 `No module named 'PIL'`、`No module named 'numpy'`；换了三四个解释器都不行，中途还自己手写脚本绕过，结果绕过的版本少了主体框检测、且文件名排序与记录顺序可能对不上。
**根因**：技能依赖 PIL + numpy，宿主把包放在 `resources/packages/pip/local/sets/<hash>/`，需要 `PYTHONPATH` 指向**同时含 PIL 与 numpy 的那个集合**再配运行时解释器。我没有先一次性探明环境，而是逐个试错。
**教训**：
- 动手前**先一次性探明运行环境**：遍历候选解释器与包集合，打印各自具备的库，选定后就固定复用，不要每步重猜。
- 已知可用组合（本机实测）：解释器 `resources/runtimes/python/3.14.6/bin/python3` + `PYTHONPATH=resources/packages/pip/local/sets/93d8ccef52e9fb999777d713facae11c`（PIL 12.3.0 / numpy 2.5.3）。环境变化时重新探测，但**探测一次、记录结果**。
- **不要为了绕开依赖而自己手写替代脚本**：绕过的版本会静默丢掉主体框检测、排序一致性等既有保证。缺依赖就去修环境，而不是简化流程。
- 若确实要手写替代，**必须逐条验证与记录的一一对应**（id 序列 == 源文件名序列、宽高比逐张比对），不能只抽样看前三个。

## 13. 串行上传与串行校验，往返次数被放大

**现象**：104 张素材被拆成 5 批串行上传，加上逐张 curl 校验外链，光这两项就占掉大几分钟。
**根因**：`upload_asset.py` 支持一次传多个文件（`sys.argv[1:]`），我却分批多次往返；外链校验用 `while read + curl` 串行，104 个链接 10 秒，而 `xargs -P 8` 并发只要 1 秒。
**教训**：
- **上传一次传一批**，不要人为拆分往返。路径要逐字从清单文件读取，不要手敲（手敲 41 条曾有大量不存在的路径）。
- **任何「对 N 个 URL 逐个请求」的校验都必须并发**。技能已提供 `scripts/check_urls.py`（标准库、8 路并发、URL 去重、能识别几百字节的错误响应页），208 个链接 3 秒。
- 宿主注入的上传 SDK **无法被外部包装器并发调用**（不是普通可导入模块），所以提速要落在「减少往返次数」与「并发化自建校验」上，而不是包装上传脚本。

## 14. 脚本报错却报成「验证通过」

**现象**：我说「四视口验证门全部通过」，实际那次 `verify_layout.mjs` 因 `screensCap` 引用了尚未声明的 `N`（TDZ 错误）直接抛异常退出，一行断言都没跑到。
**根因**：用 `grep -E "FAIL|==>"` 过滤输出，**空结果被我当成了「没有失败」**。过滤把错误信息也一并滤掉了，退出码没检查。
**教训**：
- **空输出 ≠ 通过。** 任何带过滤的验证命令，必须同时检查退出码，并确认「预期会出现的成功标记」确实出现了（如 `==> 全部通过` 的行数应等于视口数）。
- 汇报验证结论前，先看**未过滤的原始输出尾部**。过滤是为了读得清爽，不是为了得出结论。
- 这条与案例 8 同源：**验证工具本身也会坏**。工具抛错时，最危险的不是失败，而是把失败误读成成功并对外宣称达标。

## 15. 断言读了一个引擎里根本不存在的变量

**现象**：`verify_layout.mjs` 的「兜底放置 = 0」一直打印 `0/0/0`，我据此多次宣称该门通过。实测开启计数后，v1 基线桌面有 2–3 张、手机有 10–13 张被延底垫放堆在画布底部。
**根因**：断言用 `vm.runInContext("typeof FALLBACK_N==='number'?FALLBACK_N:0")` 取数，而**模板里从未声明 `FALLBACK_N`**。`typeof` 对未声明变量返回 `"undefined"`，三目永远走 `:0` —— 断言恒真，从未测量过任何东西。v23、v1、历次四视口验证全被它骗过。
**教训**：
- **恒真断言比没有断言更危险**：它给你虚假的安心，还让你对外做了不实陈述。任何"从被测代码取数"的断言，必须先用一个**已知会失败的输入**验证它真能失败（本例：故意垫底几张，看计数是否非 0）。
- `typeof x === "number"` 这类防御写法会把"变量缺失"静默降级成"值为 0"。取数失败应当**报错**，不该兜底成通过值。
- 修计数后记得同步修**所有**垫底路径：随机放置兜底与自愈重放是两处独立的延底垫放，漏掉任何一处都会漏报。

## 16. 振幅断言冒充速度断言，把"更快"判成"退步"

**现象**：密度 +20% 后「漂移行程 ≥40px」全线失败，看似运动退化了；实测速度却涨了 20–40%。
**根因**：该断言量的是 `2 * t.rx`（**振幅**），与频率无关。而密度提高必然压缩间隙，轨道半径 = 间隙/2，故振幅必降 —— 任何有效的密度提升都会触发这条"失败"。用户要的"运动更明显"是**速度**（px/s = w·r），不是振幅。
**教训**：
- 断言指标必须对应**用户可观察的语义**。用户说"动得更明显"，指的是单位时间位移；说"漂得远"才是振幅。两者方向可能相反。
- 零相交只取决于半径 r，与频率 w 无关 —— 所以「提频提速」是密度与速度可以兼得的唯一通道；任何把二者绑死的指标都会错杀正确方案。
- 阈值要**尺度无关**：改用「速度 ÷ 图块宽」（v23 实测 0.025–0.032，下限取 0.020）而非绝对像素，否则换张数/视口就失真（与案例 9、13 同源）。

## 17. 中位数断言掩盖少数静止图；搬迁不是解，提频才是

**现象**：用户两轮指出"有几张图完全不动"。我的断言两轮都通过：先因阈值 1px 太松（案例 16 的余波），改成速度断言后仍通过——因为它只看**中位数**。实测桌面每页 7–9 张峰值速度仅 1.1–2.5px/s，中位数却高达 5.97px/s，把问题完全盖住。
**根因（三层）**：
1. **统计量选错**：中位数天生掩盖尾部。用户一眼看到的是"那几张"，指标必须看**最差值**。
2. **可感知阈值定太低**：我用 4px 振幅当"静止"线，而 180px 宽的图块漂 ±4px 肉眼无感。实测正常块峰值 6–8px/s、最弱块 1.1–1.7px/s，差距 4 倍——该按**速度**定线（桌面约 ≥2.6px/s）。
3. **解法方向错**：我第一反应是 `fixWeakMovers` 搬位置，实测只把弱动占比从 2.0% 降到 1.5%——因为高密度下**整条带都被包夹**，搬去哪都差不多。分离余量 ≈ `(gap+gap)/2+2*RES`，预算 = 间隙/2，振幅被密度锁死，这是结构性的，调参救不了。
**正确解**：提频。可感知性 = 频率 × 半径，而零相交只取决于半径。给弱动块单独放大 `wx/wy`（`px` 范围不变 → 保证不受影响），`weakRatio=0.72` 让最慢块 1.11→4.00px/s，且只动约 26/104 张、保住参差感。
**教训**：
- 用户说"有几张不动"，断言就必须是**逐块最差值**，任何中位数/均值都会漏。校准断言时用「已知有问题的版本必须 FAIL、修好的版本必须 PASS」来验证判别力。
- 密度与振幅零和、但与速度不零和 —— 遇到"更密还要更动"，先想到**频率**这个免费维度，别去动半径或间距。
- 搬迁类修复要先证明"存在更松的位置"。若整个可行域都被包夹（本例），搬迁是无效功，早点用数据否掉。

## 18. 「统计上随机」不等于「肉眼看得出变化」——两轮返工的完整链条

**现象**：用户要求刷新时图片尺寸随机。第一轮：把 hash 改成 `Math.random()`，我测「宽度是否变化」→ 104/104 变，宣布修好。用户看后说"只在两个固定尺寸之间来回切换"。第二轮：我测出钳位堆积并改为无尖峰区间映射，测「distinct 值个数」→ 每图 35–52 个，宣布修好。用户还是说"每次刷新看不出变化"。第三轮才真正解决：localStorage 记住上次宽度 + 强制跳变 ≥18%，用**接力刷新模拟**验证（12 次加载 0 违规、0 乒乓、单图每变 ≥19.8%）。
**根因（三层递进）**：
1. **指标选错两次**。"是否变化"（第一轮）与"distinct 个数"（第二轮）都不是用户感知的量。用户感知的是**相邻两次加载的差距是否肉眼可辨**——必须测「接力链条中相邻宽度的变化率」，且用 localStorage 桩真实复刻记忆传递。
2. **钳位堆积**：「生成→钳位」把一整段 hash 坍缩到同一边界像素值（30% 加载恰好=128px），distinct 再多也集中成两档尖峰。正解是先算无钳位可用区间再连续映射。
3. **概率不保证体验**：即便分布连续，多数加载的相邻差距仍可能小到无感。要"每次都看得出"，就得把保证做进机制（记忆+最小跳变），而不是调分布。
**教训**：
- 用户描述现象（"在两档之间切换"）时，**按现象选指标**：他说的"两档"= 前 N 个高频值的覆盖比例，第一反应就该测集中度，而不是数 distinct。
- 验证「跨加载行为」必须模拟加载链条（记忆传递），单次加载的仿真测不出乒乓与堆积。
- 两轮"数据说修好了、用户说没修好"之后，第三轮我停止解释、直接换机制并把保证做进代码——当测量与用户感知反复冲突时，**升级机制比继续调参更快**。
- 退化路径要显式设计：手机带太窄放不下 18% 跳变时退化为带内随机、隐私模式无记忆时退化为普通随机，退化后仍满足"在范围内、每次都变"。

## 19. 「功能入技能」不等于「调优成默认」——用户主动发现，我未自查

**现象**：用户问"密度 +27%、速度 +20% 有没有写进技能？"我一查：机制全在，但 12 个参数默认值**全是保守的 v2 值**（`spacingFactor:1`、`randomSize:0`、`fix*:false`）。照默认跑一遍，产出的是 v2 的老样子，不是用户验收过的那版。若没被问起，下次测试跑就会静默交付错误基线。
**根因**：我把"加开关"当成了"完成集成"。为了保住 `check_equivalence.cjs` 这道等价门，我把每个改动都做成默认关闭的开关——这个决定本身是对的，但**只做了半边**：机制入库了，用户认可的那组值没跟着成为默认。
**正解（已实施）**：调优值固化成 `assets/config.approved.json`，由 `build_page.py` 构建期自动注入；引擎 CFG 默认仍与 v23 逐字一致，等价门继续有效。二者解耦：基线可验、成品是验收过的样子。另加 `--no-preset` 复现基线、`--config` 单项覆盖。
**教训**：
- **加完开关必须回答：默认走哪条路？** 用户要的是行为改变，不是"多了一个能力"。开关默认关闭 = 行为没变 = 任务未完成。
- 「保守默认 + 显式开启」与「验收值作默认」并不冲突：把两者分层——引擎默认守基线，构建预设给验收值——就能同时满足。
- 集成类任务收尾要自查：**用默认参数跑一遍全流程**，确认产出就是用户认可的那版。别只确认"代码在里面"。
- 同一轮还踩到配套陷阱：`verify_layout.mjs` 的 config 取自**第二个参数（数据文件）**而非入口页，用空 config 的数据去验预设页会假失败（同页 15/15 vs 2 项 FAIL）。已在 sop.md 标注。

## 20. 注入站点时双挂载并存（按注释标记剥离，漏掉无标记的旧块）

**现象**：点开一只生物出现 **8 张** `.kinfig`（4+4），且 src 混合（一份用整帧 CDN、一份用主体裁剪）。
**根因**：早先把挂载脚本放在 `</body>` 之前且**没有标记**；后来的注入器只剥离「标记之间」的内容，
于是旧挂载块留在文件里，与新块并存——两份各自建了一条胶片条、各自绑了钩子。
**教训**：
- **按内容特征识别，不按注释标记。** `inject_kinship.py` 用 `PlaygroundKin|__KIN_GROUPS__|__KIN_CROPS__|kinwrap`
  匹配 script 块并全部移除，再追加唯一新块；移除数会打印，>1 说明之前确有残留。
- 注入后必须**断言唯一性**：挂载特征块数 == 预期（有分组 2 块 / 无分组 1 块），
  `PlaygroundKin` 定义数 == 挂载层源码里的定义数（**从源码推导，不写死为 1**——降级分支也有一处定义，
  我曾写死 1 而误判失败）。
- 幂等注入要能重复执行而不累积。

## 21. JS 写成 Python 式相邻字符串拼接，整个 script 块静默失效（同一错误犯两次）

**现象**：页面毫无反应，控制台 `Uncaught SyntaxError: Unexpected string`，网格/条带一张都不渲染。
**根因**：把 Python 的隐式相邻字符串拼接 `"a"\n"b"` 写进 JS。这在 JS 是语法错误，
会让**整个** `<script>` 块失效——症状不是局部功能坏，而是全页静默无反应，极易误判成数据问题。
两次分别在导出说明常量与 corrections 的 note 字段。
**教训**：
- **要注入站点的 JS，注入前必须 `node --check`**（铁律 8）。这是唯一拦住第二次同类错误的手段。
- 自查模式：grep「行尾引号 + 下一行行首引号」的相邻字符串。
- 同类陷阱：Python 的 `global` 声明必须在**首次使用之前**——`argparse(default=K_NEIGHBORS)`
  已经是一次读取，把 `global` 放在它后面直接 SyntaxError。
- 教训的教训：**「文件写出来了」不等于「能跑」**。本项目多次因只验证产物存在、没验证执行而误报成功
  （另见 #14、#24）。

## 22. 用主体裁剪解决「对不齐」，结果过裁失真被用户否决

**现象**：用户指出条带里的图「被放大、过度裁剪，生物大得不真实，分辨率也降了」，要求回退到上一版。
**根因**：条带原本显示整帧照片，生物在各自原图中的构图位置不同（有的横构图偏一角、有的竖构图居中），
排成横向带子就高低参差。我为消除参差改用 640px **主体居中裁剪**——参差是没了，
但代价是生物占满画框、失去黑水语境、放大后不真实，且 640px 源低于显示需求。
**教训**：
- **「对不齐」要先分清是 bug 还是构图差异。** 这里是后者：整帧构图本来就各不相同，
  用裁剪强行统一 = 用失真换整齐。用户要的是真实比例 + 黑水语境，不是整齐。
- 与铁律 2 同源：**裁剪类操作对「透明生物 + 黑水」素材天然危险**，而 box 本就只该用于尺寸校正。
- 顺带查实（已写进 kinship.md 防止改回）：`r.full` 是**整帧**高清图（实测 2745×4117，比例 0.667），
  **不是**主体裁剪；焦点图若换用它，会重现错位 + 长宽比跳变 + 白下载一张巨图。
- 也纠正我自己的错误估算：焦点图实际只显示约 423px 高（38vh×1.22），640px 源是 0.66× **缩小**，
  根本不存在「放大模糊」。**先量再改**——凭估算加逻辑会加出不必要的复杂度。
- 用户否决一个方向后，**逐字回退到上一版**（图源 + 尺寸都回退），只保留他明确认可的部分
  （滑动平移、无闪烁关闭），不保留「我觉得更好的」残余（铁律 7 的同源应用）。

## 23. 聚类阈值扫描完全无效：地面真值同簇率恒为 2/8

**现象**：想让算法自动判定「同一生物」，扫了 0.08→0.40 七个阈值，**地面真值同簇率始终是 2/8**；
thr=0.13 时还产出 55 张的巨簇、簇内最大距离 1.0。
**根因（三层）**：
1. **单链接聚类的链式膨胀**：A像B、B像C 就把 A-C 连进来。阈值越松簇越大，垃圾也一并进来。
   改全链接（簇内每对都须 ≤ 阈值）后巨簇消失，但同簇率仍不改善。
2. **特征自身两个 bug**：① topo 特征含**包围盒长宽比**，对旋转敏感——同一只栉水母转 45° 后
   topo 距离 1.60，把地面真值对拖垮；② Hu 矩用 `min(d,1.5)` 硬钳位，大量对顶到上限，
   恒定贡献 0.33 的**噪声距离**，淹没有判别力的项。修掉这两条后召回 38%→50%。
3. **三维姿态剧变纯几何认不出**：八腕幼体三帧 spec 0.44–0.72，樽海鞘两帧因变焦 spec 0.76。
   人靠「八条腕＋橙色色素环」认得，轮廓投影却完全不同。
**教训**：
- **有地面真值时，先量召回率再谈方案。** 这里的地面真值唾手可得（同潜次内 ≤10 秒的连拍簇
  ≈ 必然同一个体），它一次性否掉了「聚类自动判定」整条路线。
- 召回率与同簇率是两个量：宽网能把召回做到 88%，但同簇率不随之改善——
  **放宽阈值不解决判别力，只是把垃圾并成大簇**。
- 正确架构是**算法召回 + 人眼判定**（铁律 9）。当测量与目标反复冲突时，升级机制比调参快（同 #18）。
- 特征设计：**旋转敏感量必须剔除**；**钳位不是归一化**（改用 z-score + tanh 压缩）。
- v1 的颜色主导权重（0.42）同样被否决：黑水照片里所有胶质生物都是「黑底上的半透明白蓝」，
  实测把螺壳、水母钟、带棘幼体、章鱼聚成一簇且 maxd=0.096（全场最低）。颜色只配当辅助（0.12）。

## 24. 测试脚手架自身出错，多次把正确实现判成失败

**现象**：功能实测全通过，但断言报了多次假失败；另有一次真失败被我误读成通过。
**假失败的来源**：
1. **Node 内置 WebSocket 用 DOM API**（`onopen`/`onmessage`），不是 `ws` 包的 `.on()`——直接崩在连接阶段。
2. **合成事件传播路径**：站点 `keydown` 挂在 **window** 上，`document.dispatchEvent(...)` 不带
   `bubbles:true` 到不了 window；`({a:1})()` 这种把对象字面量当函数调用也是纯语法错。
3. **断言基准写错**：以为「点第 3 个邻图」会切到某张，实际成员顺序里第 3 个是另一张；
   以为文献库应显示 38 条，实际按设计显示 34 条唯一书目（38 是引用出现次数，口径不同）；
   以为 `PlaygroundKin` 只定义 1 次，实际降级守卫分支还有一处。
**真失败被误读成通过**：`node ... | tail` 管道下 `$?` 取到的是 **tail** 的退出码，
一次致命环境错误（找不到页面）被报成「退出码 0」。
**教训**：
- **断言失败先怀疑测量方式，再怀疑产品**（#8、#14 同源）。这是本项目最高频的错误类型。
- 断言基准要从**数据推导**，不要凭记忆写死：测试组应动态取「成员最多的组」，计数由它派生；
  页面匹配子串做成环境变量（`MATCH`），否则换个文件名就「找不到页面」。
- **管道会吃掉退出码**：把输出写文件再读，或直接取 node 退出码（0=全通过 / 1=断言失败 / 2=环境问题）。
- 其他实测坑：`tileById()` 返回的 tile 对象**没有 src 字段**（URL 在 `Playground.records`）；
  CDN 图片会**污染 canvas**，任何 `getImageData` 像素检测都会 SecurityError；
  `--screenshot` 会**另起一次干净加载**，拍不到需交互才出现的界面——必须用 CDP 在活实例上
  `Page.captureScreenshot`；`--dump-dom` 的 HTML 含**内联脚本自身的源码文本**，数 DOM 元素会假阳性
  （实测 `class="tile"` 数到 1，真实渲染 0 个），必须先剥掉 script 内容再数。
