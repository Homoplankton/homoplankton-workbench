# Plankton Playground

把一批黑水浮游生物照片变成"生物漂浮在宇宙里"的可滚动作品集页面。

本技能的核心价值不是"会做漂浮动效"，而是两条已被 20+ 轮迭代验证过的硬约束：

1. **图框级零相交**：任何时刻、任何两张图的完整矩形都不相交（不是主体不重叠，是用户眼睛看到的框不重叠）。
2. **交付前真实验证**：必须跑运行时仿真 + 合成预览图亲眼确认，语法通过 ≠ 能看。

引擎已定型在 `assets/playground.html`（v23 基线），**不要重写算法**。调参数、换数据、挂钩子即可。

---

## 何时使用

- 用户给出图片文件夹，要求生成漂浮式作品集 / 落地页
- 用户在已有 playground 上要求调密度、尺寸、漂浮幅度、背景、边距
- 用户要求基于 playground 增加新功能（元数据面板、谱系聚类、筛选等）
- **用户要求"点开一只生物时同时显示同一生物的其他角度"** → 走 S6（关联条带）

不适用：需要真实后端、数据库、支付、鉴权；与图片漂浮无关的页面。

## S0 需求锁定（一轮问全）

必须一次问清，不要边走边问。缺失项用 `references/sop.md` 的 v23 默认值并声明假设。

需要确认的槽位（按返工代价排序）：

1. **图片文件夹路径** —— 找不到就先定位，别猜
2. **是否已人工筛选** —— 决定要不要跑 S1.0 背景筛选
3. **重叠口径** —— 默认"图框零相交"；若用户说主体不重叠，说明羽化暗边可交叠并告知风险
4. **尺寸带** —— 默认桌面 162–206px
5. **左右禁飞区** —— 默认桌面 70px
6. **密度** —— 默认空隙率 1.5
7. **素材尺寸策略** —— 默认显示层 ≥1MB、灯箱用完整原图；文件夹 >200 张时必须停下报告上传量与首屏负载（见下）

**规模闸门（强制）**：文件夹超过 200 张时，先算 `张数 × 单张均值`，把预估上传体积、上传耗时量级、首屏并发加载数告诉用户，由用户决定继续还是降规格。不得静默按 ≥1MB 处理千张级素材（≈5GB 上传、低端机可能卡死）。

## S1 素材准备

### S1.0 背景筛选（仅当文件夹可能混有非黑水图）

先判断是否需要：抽样 30 张看边缘近黑占比分布，若双峰明显且暗峰占比 >90%，说明已筛过，跳过。

需要时跑 `scripts/screen_blackwater.py`，它输出三类：明确黑水 / 明确非黑水 / **灰带**。灰带必须逐张合成拼图给用户或自己肉眼判定——这是唯一可靠的方式，纯算法在"白天打光压暗背景的微距照"上会失败（历史上真实踩坑）。

筛选结果给用户一份清单（含剔除原因），不要静默丢弃。

### S1.1 去重与抽样（张数超需求时）

1. **变体合并**：同 stem 的 `-Edit`/`-Edit1`/`Enhanced-NR`/`copy`/尾数字 → 归一，取文件最大者
2. **连拍归组**：同 (年, 月) 且相机序号差 ≤4 → 并查集归组，每组取一张
3. **均衡抽样**：按 类目 × 主色调 双层轮转抽取（类目来自原目录名或 sidecar；色调由 HSV 中位色相分桶）

抽样数由 S0 确认；默认全部使用。

### S1.2 素材生成

跑 `scripts/prep_assets.py`，产出：

- **显示层**（浮动元素）：默认长边 ≤900px、质量 86；若 S0 选了 ≥1MB 策略，按质量阶梯（2000/1800/1600/1400/1200 @ q92–96）找到首个 ≥1MB 的档位，找不到就用原图
- **灯箱层**：完整原图逐字节复制（`shutil.copy2`），不重编码
- **主体框 box**：自动阈值（`mean + 3σ`）量非黑内容包围盒 + 6% 外扩，归一化存四元组；用于尺寸视觉校正（主体小的图放得更大，让屏幕上"动物"大小参差而非图框参差）

> ⚠️ box 只用于**尺寸校正**，不用于裁切，也不用于碰撞判定。裁切会切掉透明生物的淡边缘（铁律 2 的由来）。

### S1.3 上传与数据文件

用 apps-builder 的 `upload_asset.py` 上传两层素材，产出 `data.js`：

```js
window.PLAYGROUND_DATA = {
  schema: "plankton-playground/v1",
  title: "...",
  config: { /* 覆盖 CFG 默认值，可留空 */ },
  records: [{
    id, src, full,          // 显示层URL / 灯箱原图URL
    w, h,                   // 显示层像素尺寸
    box: [x0,y0,x1,y1],     // 主体框（归一化），可为 null
    attrs: {}               // 任意业务数据，引擎只透传
  }]
};
```

**attrs 是扩展的唯一入口**：预处理阶段应把能自动拿到的元数据（EXIF 拍摄时间/相机、目录名推断的类目、用户提供的 sidecar CSV/JSON 的任意列）全部塞进 `attrs`，即使当前页面不用。将来加功能只是"渲染已有数据"，不需要重跑素材。

## S2 生成页面

跑 `scripts/build_page.py --template assets/playground.html --data data.js --out <入口.html>`：注入标题、数据引用、config 覆盖，不触碰引擎算法。

引擎已固化的机制（**不要改**，只在必要时调 CFG）：

| 机制 | 作用 |
|---|---|
| 分带轮转放置 | 大小图混排进每个纵向带 → 消除"上大下小"梯度 |
| 聚簇偏置 60% | 局部成团、局部留白 → 有节奏不死板 |
| 锚点自愈重放 | 放置失败时全局重找位，不堆到底部 |
| 图框级不动点预算 | 漂移额度按实测间隙迭代收敛 → 任意帧零相交 |
| 非对称包络 | 朝空档方向漂得远、贴邻居一侧漂得少 |
| 保险丝推挤 + 钳回预算框 | 兜底残差，不破坏几何保证 |
| 星尘两层 | 纯白锐利小点，无柔斑、无前景脏点层 |
| 整层一次浮现 | 首屏集齐后统一淡入，无逐张出现、无闪烁 |

**扩展方式（未来任何功能都走这里，不改引擎）**：

- 数据：写进 `record.attrs`，引擎原样透传
- 交互：`Playground.on("lightbox:before" | "lightbox:open" | "frame" | "reveal" | "relayout:*", fn)`
- 重组：`Playground.relayout(kind, keyFn)` 换排序键；`Playground.setTargets(spec)` + `CFG.morph>0` 做平滑过渡
- 参数：`Playground.setConfig({...})` 运行时改，自动重排

引擎不认识任何业务语义（分类、地点、深度都只是 attrs 里的字符串），所以加功能不需要动地基。

## S3 验证门（不可跳过）

```bash
node scripts/verify_layout.mjs <入口.html> <data.js> --vw 1440 --vh 900 --seeds 5 --frames 601
```

必过断言（任何一条失败都不许交付）：

- 记录数 = 素材数
- **601 帧逐帧图框零相交**（穿透 ≤1px）
- 轨道包络不越画布、无越界
- 左右禁飞区零侵犯
- 首屏图数达标、上下密度均匀、大小梯度 <1.5、底部无堆积
- 兜底放置数 = 0（>0 说明画布容量不足，密度参数过激）
- **无弱动图块**（逐块峰值速度 ≥ `max(1.5, 视口宽×0.0018)` px/s）
- **无静止图块**（合振幅 ≥1px）
- 运动反同步（同一时刻左右方向都有足量图块）

> ⚠️ 弱动/静止两条必须看**逐块最差值**，不能用中位数：中位数天生掩盖少数被四面包夹的图块，
> 而用户一眼就看得见"那几张锁住不动的图"。断言校准方法：拿一个已知有问题的版本跑，
> 它必须 FAIL；修好的版本必须 PASS。只有能区分两者的断言才算有效（见 lessons #15–17）。
>
> 兜底放置的已知豁免：手机视口（≤390px）受容量极限，实测会有 3–4 张垫底（v23 基线是 10–13 张）。
> 只要「底部无堆积 ≤1.4×」通过，即可交付，但**必须在取舍声明里如实写明**。

多视口都要跑：1440×900、1280×680（常见笔记本）、1920×1080、390×844（手机）。
用户指定具体机型时按该机型视口跑（如 iPhone 16 Pro Max = 440×956，此前未覆盖过）。

另有 `scripts/check_equivalence.cjs`：改了引擎后用它证明 morph=0 时与 v23 基线逐帧坐标一致（偏差 <0.01px）。**任何触碰引擎的改动都必须过这道门。**

## S4 视觉自评门（不可跳过）

```bash
python3 scripts/render_preview.py <入口.html> <data.js> <素材目录> --out preview.png
```

按布局坐标 + 真实图片合成首屏（和滚动中段/末段）预览图，**用 Read 工具亲眼看**，检查：

- 是否有矩形边框可见（羽化不足 / 底纹反差）
- 是否有大片空白或局部堆叠
- 大小是否有参差、横竖是否混合
- 上中下三段密度与尺寸是否均匀

看到问题就修，修完重跑 S3。**不许因为"仿真通过"就跳过这一步**——历史上全黑页面和方框叠方框都是仿真没覆盖、只有眼睛能发现的。

## S6 关联条带（可选功能层）

**触发**：用户要求"点开一只生物时，同时显示同一生物的其他角度"。
完整细节见 `references/kinship.md`，这里只列骨架与不可省的判定。

### S6.0 先确认口径（不做这一步必返工）

「同一生物」必须问清，默认口径是 **同性别 + 同发育期 + 形态相似**：

- 跨性别不归组（船蛸雌雄异形）
- 跨发育期不归组（无壳幼体 vs 有壳雌体，即使同种）
- 近缘种不归组

若用户其实想要"同物种的全发育阶段"，那是**生长序列**（另一个工具），不是这个条带——先纠正再动手。

口径确认后有个直接好处：视觉相似度就是主信号，**不需要物种级鉴定兜底**。
物种级鉴定实测 0/10 能定到种，但"看起来像不像"不需要定到种。

### S6.1 召回 → S6.2 接触表 → S6.3 人工核验

```bash
python3 scripts/kin_features.py <主体裁剪目录> --out <项目>/kin_features.json [--limit 40]
python3 scripts/kin_sheets.py <项目>/kin_features.json <主体裁剪目录> --out-dir <项目>/review_sheets
```

然后**用 Read 工具逐张看接触表**，判定每组是 coherent / mixed / rejected，手写 `kinship.json`。

> ⚠️ 铁律 9 的实测依据：以连拍簇为地面真值（同潜次内 ≤10 秒 = 几乎必然同一个体），
> 紧阈值召回 50%、宽网召回 88%，但**任意阈值下"同簇"率恒为 2/8**。
> 放宽阈值只会把垃圾并成大簇（thr=0.13 时产出 55 张巨簇、簇内最大距离 1.0）。
> 所以算法永远只能召回，**判定必须人眼做**。

主体裁剪只用于**算特征**，绝不用于显示（铁律 10）。裁剪可以复用 S1.2 素材，
或单独生成一套长边 1200 的主体框 +12% 留边裁剪。

### S6.4 注入

```bash
node --check assets/kinship_mount.js          # 铁律 8，必做
python3 scripts/inject_kinship.py --mount assets/kinship_mount.js \
        --groups <项目>/kinship.json --targets <站点.html> [<站点副本.html> ...]
```

注入器按**内容特征**剥离旧挂载块（不是按注释标记），并断言块数与 `PlaygroundKin`
定义数。没提供 `--groups` 时挂载层整体静默关闭，站点退回纯漂浮长卷——这是正确降级。

### S6.5 实测（必须真实浏览器）

```bash
CHROME --headless=new --remote-debugging-port=9381 file://<站点.html> &
PORT=9381 MATCH=<站点文件名子串> node scripts/test_kinship.mjs
```

26 项断言覆盖：条带张数、图源是整帧、焦点纯 transform 放大、触控板平移与吸附、
点邻图不重建 DOM、关闭无闪烁、无关联组回退单图、指认合并即时生效。

> ⚠️ **必须检查 node 的真实退出码**（0=全通过 / 1=断言失败 / 2=找不到页面）。
> `node ... | tail` 管道下 `$?` 取到的是 tail 的退出码，会把致命失败读成"退出码 0"（lessons #14 同源）。

### S6.6 条带 UI 约定（用户已验收，勿改）

| 项 | 约定 |
|---|---|
| 图源 | 整帧展示层 `r.src`（**不是**主体裁剪；裁剪版过裁失真已被否决） |
| 焦点放大 | 纯 `transform: scale(1.22)`，布局零位移。**不做**全分辨率升级 |
| 边界 | 居中锁定：首/尾图另一侧留白，焦点永远在正中 |
| 排列 | 保留错落（奇偶 ±stag 上下错位） |
| image ID | 完全不显示（无 figcaption / 无 title / alt 空） |
| 关闭 | 延迟 460ms 清理，覆盖 `#lb` 的 0.4s 淡出，避免闪现上一张主图 |
| 无关联组 | 不进条带，走引擎默认单图 |

## 参数速查

| 参数 | 默认 | 说明 |
|---|---|---|
| `loF` / `hiF` | 0.113 / 0.143 | 尺寸带（视口宽占比），桌面 ≈162–206px |
| `MX` | 70（手机 24） | 左右禁飞区 |
| `E` | 6（手机 4） | 上下边缘安全距 |
| `voidRatio` | 1.5 | 画布空隙率。**不是密度主杠杆**：调小只让画布变矮，密度增益封顶且堆底上升 |
| `RCAP` | 46（手机 26） | 单侧漂移上限 |
| `RES` | 15（手机 10） | 每侧最小跑道 |
| `gapMin`/`gapSpan` | 6 / 8 | 呼吸间距 6–14px |
| `wxLo..wyHi` | 0.05–0.22 | 漂移角频率（周期 30–150 秒） |
| `dustN` / `sparkleN` | 460 / 46 | 星尘数量 |
| `morph` | 0 | >0 启用重组插值 |
| **`spacingFactor`** | 1 | **密度主杠杆**：<1 按比例收紧 RES 与 gap。实测 0.45 → 密度 +27% |
| **`speedFactor`** | 1 | 速度倍率：只缩放角频率，不动振幅，不影响零相交 |
| **`weakRatio`** | 0 | >0 启用逐块速度下限 = 本页速度中位 × 此比例。0.72 → 最慢块 1.1→4.0px/s |
| `speedFloorCap` | 6 | 单块提频倍率上限，防抖动感 |
| `fixScreensCap` | false | 修「屏数上限绑定→底部堆图」 |
| `fixFallbackScan` | false | 修「兜底扫描步长过粗→明明有位却垫底」 |
| `fixOrbitRadius` | false | 修「半径用 min(L,R) 而非 (L+R)/2 → 图块锁住不动」 |
| `loadConcurrency` / `lazyMargin` | 6·4 / 1.0 | 分级加载并发上限与滚动提前量（只影响何时下载，不影响布局） |
| **`randomSize`** | 0 | 1=每次刷新重抽尺寸（默认 0：尺寸由图块序号固定，仅位置随机） |
| **`sizeSpread`** | 1 | 尺寸带展宽倍率（绕带中心对称）。原带比值仅 1.27，须 >1（实测 2.6）才看得出变化 |
| **`sizeJumpMin`** | 0 | 强制跳变比例：本次尺寸须与上次相差 ≥ 此比例。建议 0.15–0.25；0=普通随机 |

调参顺序建议：先 `spacingFactor`（密度）→ 再 `speedFactor`/`weakRatio`（动感）→ 最后 `loF`/`sizeSpread`（尺寸）。每调一项跑一次 S3。

**刷新随机尺寸（v3 新机制）**：开 `randomSize=1` 后，页面把每张图的宽度记进浏览器 localStorage，
下次刷新只在「与上次相差 ≥ `sizeJumpMin`」的子区间内重抽 —— 让"每次刷新尺寸都看得出变化"由**机制保证**，
不靠概率碰运气。尺寸仍严格落在 `sizeSpread` 决定的范围内，位置照旧每次随机。
验证用 `scripts/reload_chain.cjs`（接力刷新模拟，逐次核对跳变保证/越界/乒乓振荡）。
两个已知边界：① 手机尺寸带太窄（约 32px）时 18% 跳变可能放不下，机制自动退化为「带内均匀随机」（仍在范围内、仍每次变）；
② 隐私模式无 localStorage 或首次访问，退化为普通随机。默认路径（`randomSize=0`）与 v23 逐帧等价，已四视口验证 0.0000px。

三个 `fix*` 开关默认关闭以保持与 v23 逐帧等价。**开启后等价性校验会失败，这是预期而非回归**，
此时改用「相对上一版实测对比」验收（工具见 `history/v2/` 与实验脚本）。
密度与**振幅**零和，但与**速度**不零和——零相交只取决于半径，故提频是唯一能「又密又动」的通道。
